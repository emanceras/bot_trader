# Engine reuse assessment

**2026-10-18 · Phase III.A · documentation assessment, no engine installed or benchmarked.** [Español](../../es/architecture/engines.md). Ten official source snapshots and directed reading events are recorded in [engine-sources.jsonl](../../architecture/engine-sources.jsonl). Their hashes identify the material actually examined; the URLs track branches and can change. This review adds no academic studies or financial results to the existing corpus.

## Decision

Keep the research contracts, provenance, protocol controls and interface independent of an engine. For III.B, implement a **bounded, deterministic synthetic accounting harness** to test those contracts, with an explicit capability declaration and a replaceable engine boundary. It is a test implementation, not a proprietary production trading engine or a validated market simulator. No market-data fetching, exchange adapter, broker credential, live order endpoint or paper-trading loop belongs in that implementation.

For a later authorized financial evaluation, prefer adapting an existing engine over building a general execution engine. **NautilusTrader and LEAN are the first alternatives to evaluate against the chosen instrument and event semantics; neither is selected or certified now.** Freqtrade is a conditional alternative for a compatible crypto workflow. vectorbt can be an optional research library with carefully controlled search and license review. Backtrader provides useful design patterns and a possible simple comparator, subject to compatibility and maintenance checks.

This is not evidence that a custom simulator is superior. The narrow harness avoids committing to an execution model before data, instruments and protocols are settled, while exercising persistence and accounting now. Its growth is bounded: derivatives margin, liquidation, queue position, order-book reconstruction, asynchronous venues and realistic partial fills require a new engine decision; they cannot accumulate as ad hoc extensions. If even the stated synthetic contract needs such semantics, stop and revise this decision before claiming coverage.

A framework's “dry-run” is a prospective market-connected operating mode and is outside the synthetic tests authorized here.

## Framework, library or patterns

- **Complete framework:** brings broker, accounting and order lifecycle semantics, but also dependencies and live surfaces. Adopting one later means mapping its semantics into our contracts, not replacing experiment governance with its defaults.
- **Library:** may calculate arrays, indicators or metrics without controlling the process. It still needs locked dependencies, license compatibility, causal inputs and recorded search budgets. Thousands of fast combinations remain thousands of research choices.
- **Patterns:** event timestamps, immutable inputs, capability checks, deterministic replay and separated adapters inform our own original code. No source is copied in this assessment; borrowing a pattern is not a license review of copied implementation.

## Admission tests for a later engine adapter

Before any financial use, record an exact release/commit, dependency lock, documentation version, licenses and source provenance. Evaluate only a finite set of alternatives using the same **synthetic** contract cases: decision/availability/execution ordering; USD valuation distinct from USDT/USDC; cash/inventory conservation and full fee reconciliation; reproducibility under event replay; unsupported instruments rejected; failed or cancelled runs retained. Define tolerances and accounting assumptions before comparing outputs. A disagreement requires explanation, not majority voting between engines.

Then, only with the relevant authorization and protocol, check whether the chosen engine can represent the actual instrument, total committed capital, historical specifications, settlement/funding, execution and risk assumptions. Timing precision in a type does not prove feed precision or executable latency. Fast arithmetic does not establish realistic fills. No engine automatically removes look-ahead bias, survivorship bias, multiple testing or repeated holdout use.

Keep simulation, later paper trading and later live execution as separate authorized capabilities and processes. Reusing a strategy implementation across them cannot be the authorization mechanism. III has no live implementation or credentials; an adapter that silently enables network downloads or orders is not admissible. Archive the engine's version and assumptions with every future run; status must distinguish technical test success from economic validation.
