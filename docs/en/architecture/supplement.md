## 2. Decision classes and evidence

- **A — essential now:** a contract, invariant or correction needed to make current III artifacts trustworthy or avoid encoding the wrong boundary. A may be a precise architectural constraint where no runtime consumer exists; it does not require an empty implementation.
- **B — useful, nonessential:** a small extension after demonstrated need, without delaying essential III acceptance.
- **C — future design:** specify responsibilities and admission conditions; implement only in the separately authorized phase that needs it.
- **D — do not add now:** no sufficient benefit over the simpler alternative. Reconsider only after a concrete limitation appears.

`Code/tests` below means inspected implementation and named behavioral tests, not external scientific validation. Official framework documentation establishes documented behavior and design alternatives, not that a strategy works. Source scope, retrieval receipts and limits are in the [targeted source assessment](supplement-evidence.md); earlier engine/stack/tool assessments remain the baseline. Architectural recommendations are our judgments and remain revisable with evidence.

## 4. Identity and relationship contract

Implemented as `VersionedReference` and optional `TechnicalRunSpec.hypotheses`, use **one versioned reference shape** for immutable research links: `kind`, stable internal `id`, positive `version`, `content_hash`. Resolve the exact stored version and verify its hash before freezing a run. An alias, display name, external order ID or “latest” is not a reproducibility reference. Current technical hypothesis associations are optional and explicitly mean *context linkage*, never a test or validation of H-00–H-24. Dataset references retain their existing exact version and artifact hash. Historical runs remain readable after a later hypothesis metadata version is imported. `test_supplement_hypothesis_version_change_preserves_historical_association` exercises that behavior, rejects a mismatched hash and rejects duplicate hypothesis associations; it does not test a financial strategy.

Use provider-independent internal IDs with a documented namespace/type; application-created attempts and proposals already use UUIDs. Future strategy, instance, deployment, portfolio and account identities must be stable across adapters. External identifiers are scoped references `(provider, account/namespace, entity type, external ID)` and never replace internal identity. The present provider-free hypothesis IDs and deterministic synthetic dataset IDs need no retrospective renaming.

Do not make every noun a table. A strategy definition and immutable implementation/model/configuration references can live in existing versioned documents until integrity/query requirements justify specific relational tables. An **instance** binds a strategy version and configuration for a purpose; a **deployment/session** records one activation in an environment/account context. A new version or deployment does not rewrite its instance's past. Runtime authority is a separate, revocable grant; it is not inherited from an entity name, status or former deployment.

| Required scenario | Relationship and invariant | III disposition |
|---|---|---|
| One strategy, several markets | Distinct instance IDs share a definition/version; market/universe selection is versioned configuration | Design now; no bot scheduler instantiated |
| Two versions evaluated together | Distinct immutable version references and attempt IDs; same comparison protocol where applicable | Existing versioned storage + new reference invariant; actual strategy evaluations later |
| Several strategies share a portfolio | Many assignments refer to one portfolio/account capital authority; allocations do not create cash | Design only; shared capital not supported by current synthetic single ledger |
| One strategy in several portfolios | Separate assignments/instances or deployment bindings, with independent limits and attributable virtual ledgers | Design only; no implicit shared cash or copied authorization |
| Two bots target one asset/account | Aggregate proposed intentions before venue submission under an explicit netting/priority policy; reconcile venue holdings independently | No policy selected; required before multibot execution |
| Bot changes environment | Preserve instance identity when useful, create new immutable deployment/session and separate authority/state namespace | Technical-only runtime remains the only accepted III mode |
| Retired strategy reconsidered | New review/versioned disposition cites material change and previous evidence; former grants stay expired/revoked | History retained; no reinstatement workflow now |
| Model replaced | Pin new model reference in a new configuration/version; earlier decisions retain old model/data/prompt identities | Reference design; no financial model registry execution now |

An exchange may net positions by account/instrument even when internal attribution uses virtual strategy subledgers. Virtual ownership is not legal, custodial or venue-level separation. Before netting/internalization, specify which strategy bears fees, realized/unrealized P&L, borrow/funding, margin and liquidation exposure, how competing exits are handled, and how aggregate positions reconcile to virtual contributions. Never count shared collateral once per bot. Allocation weights, bot counts and risk contributions have different denominators.

## 5. Flexible strategy boundary and lifecycle

The future logical path is universe/versioned inputs → prediction or strategy proposal → portfolio targets/allocation → independent risk decision → execution plan → venue events → reconciliation/accounting → monitoring. This is a dependency map, not a mandatory chain of eight services. A tightly coupled pair/basket strategy can emit an atomic plan with legs, constraints and exit semantics; it need not lose its hypothesis inside independent per-asset signals. Portfolio/risk/execution may reject or constrain that plan, but must not silently reinterpret its scientific meaning. Any change of intent is recorded with its policy/version and reason.

Current `Signal`/`Strategy` interfaces and the synthetic ledger exercise a narrow quantity-target contract. They do not implement general signal aggregation, capital assignment, partial fills or multibot ownership. A later general prediction/target adapter should use a new contract version while preserving the synthetic v1 consumer. No existing result needs rewriting and no unused parallel hierarchy is created now.

Keep the following axes separate:

| Axis | Example values, not operational permissions | Authority/evidence |
|---|---|---|
| Scientific assessment | proposed, insufficient data, evidence against, inconclusive, supported under specified conditions | Frozen protocol, comparisons, uncertainty and reviewer disposition |
| Implementation maturity | design, implemented, technically verified, defect identified | Version-specific test evidence and known limitations |
| Evaluation permission | absent, granted for a finite protocol, consumed, revoked/expired | Authorized actor, scope/data/budget/window; final access separately controlled |
| Execution environment | technical, historical evaluation, shadow, internal paper, testnet, live | Adapter allowlist and explicit environment grant; III accepts technical only |
| Operational state | inactive, starting, running, degraded, suspended, stopped, unknown | Reconciled runtime observations, not scientific opinion |
| Capital eligibility | ineligible, review pending, eligible under approved constraints | Account access, exposure/liquidity/capacity and independent risk approval |

A future transition record must reference prior state, requested next state, subject/version, policy/version, evidence available at the time, initiating and authorizing actors, reasons, timestamps and superseded decisions. Invalid transitions fail closed. Scientific support does not turn on a runtime adapter; technical success does not assign capital; paper success does not authorize live. Retirement preserves evidence and revokes/ends operational grants. Reconsideration creates a new review, not restoration of the old grant. Configuration is versioned prospectively; a revised policy cannot retroactively convert a failed old evaluation into a pass.

A generic configurable workflow engine is unnecessary until multiple real transition types require scheduling, retries and durable external approvals. Existing immutable records plus a small explicit transition service are the preferred first implementation when that need arises. A central decision service can coordinate records, but strategy, risk and execution authorities remain separate.

## 6. Evaluation, archives and the investigator's memory

Before financial evaluation, specify mechanism-specific data sufficiency, null/benchmark, net-cost model, uncertainty estimator, dependence and effective sample assumptions, regimes, parameter/friction sensitivity, tail risk/capacity, prospective requirements and portfolio increment. Thresholds belong to that versioned protocol and must precede the outcomes they judge. A metric may trigger review without authorizing promotion. Preserve total search/monitoring multiplicity and never make repeated “promotions” a reason to reopen the same final holdout.

Do not adopt 50 trades/90 days, six months, a universal Sharpe/Profit Factor, fixed discard percentages, 30 recovery trades, Kelly fraction or capital ladder. These can only be evaluated as explicitly justified choices for a particular mechanism. More strategies do not imply greater expected profit or useful diversification.

A historical disposition should distinguish **no demonstrated advantage**, **evidence against**, **cost/capacity infeasibility**, **temporarily nonoperable**, **redundant**, **technical defect**, **displaced by a stronger alternative**, and **insufficient data**. Preserve hypothesis/version, all experiments and examined periods, favorable/adverse/inconclusive results, alternative explanations, unresolved uncertainty, research cost/budget, decision actor, comparator, related work and material conditions for reconsideration. The existing repository remains the source of evidence; an archive is a query/view plus disposition records, not a second database containing only “losers.”

For the future AI investigator, begin with permission-filtered structured retrieval by hypothesis, immutable references, dataset coverage, failure/disposition tags and prior attempts. Add full-text search if queries justify it. Evaluate semantic retrieval/RAG only against a labeled set of retrieval needs and a simpler baseline; embeddings do not establish evidence quality or authorization. Graphs are useful only if demonstrated relationship queries cannot be served clearly by ordinary records. Continuous LLM retraining is neither required nor authorized.

Returned evidence must label **externally published claim**, **own observed technical/financial/prospective result**, **statistical inference**, **AI explanation/proposal**, and **human decision** distinctly. A generated explanation is not a verified fact. Retrieval must not expose reserved samples or hidden evaluation feedback. Reconsider a previously unproductive question only for a material change in data, mechanism, cost, regime evidence or method, with a new finite budget and comparisons—not an endless attempt to obtain a favorable result. Proposals cannot approve themselves, change policies or execute tools.

## 7. Monitoring, decisions and independent risk

Technical health concerns connectivity, freshness/latency, missing/duplicate/late events, rejected orders, state disagreement and restart/recovery. Statistical health concerns calibrated predictions, net results, turnover/costs, tails, regimes and uncertainty. Neither substitutes for the other. A healthy process can hold stale data; a drawdown can occur under an unchanged return-generating mechanism.

Distinguish changes in input distribution (**data drift**), changes in the target relationship conditional on inputs (**concept drift**), worse predictive performance against a comparator (**model degradation**), worse realized latency/fills/costs (**execution degradation**), and weakened net economic edge (**alpha decay**). One observation may have several explanations and detection is not causal diagnosis. Delayed/revised labels and data defects can mimic model failure.

Consider sequential/CUSUM-type monitoring, reference-window comparisons, parameter stability and dependence-aware uncertainty only after specifying what shift matters, baseline estimation, monitoring frequency, false-alarm budget, detection delay and remediation. Repeated rolling tests across bots/metrics consume a monitoring budget; threshold reuse does not preserve a nominal one-off p-value. Calibrate under plausible serial/cross-strategy dependence and regime variation. A warning requests review; it does not establish lost alpha or authorize liquidation. Method-specific assumptions and unknown power must be recorded.

The future decision chain is **condition → evidence → versioned policy evaluation → proposal → authorized/rejected/deferred decision → attempted action → observed acknowledgment/fills/state → reconciliation/verification**. Approval, command submission, exchange acknowledgment and verified outcome are distinct. Expiry and idempotency keys prevent stale/repeated actions. Partial, failed and unknown outcomes remain visible; “reverted” is used only when a compensating action is actually possible and confirmed. Financial actions are not database rollbacks.

Risk authority must be able to veto an individual signal using portfolio/account/global policy. Monitor, policy, authorization, action and verification remain separate responsibilities. Warning, reducing a target, blocking new orders, cancelling pending orders, reducing exposure and closing positions are different actions. Previously authorized protective policies may act automatically within their scope; an AI investigator cannot enlarge or alter them. A connectivity incident may justify blocking new orders before losses occur. When positions or venue state are unknown, stop new risk where feasible, preserve uncertainty, query/reconcile and escalate under the approved policy; blindly resubmitting or ordering an immediate close can increase exposure. No universal emergency liquidation rule is adopted.

## 8. Risk estimates, capital and realistic execution

Risk-study records should pin method/version, dataset/period, horizon, sample/dependence assumptions, seeds/parameters, estimated distribution, uncertainty, scenario definitions and resulting decision references. **Approved operational limits belong to a separate policy reference**, not an automatically accepted simulation percentile. Current drawdown, maximum historical drawdown, simulated drawdown quantile and authorized limit are different quantities. None is a loss guarantee.

IID trade reshuffling discards dependence and may be inappropriate for overlapping positions; block bootstrap preserves some local dependence but depends on block choice and available sample; regime conditioning depends on causal regime identification and adequate episodes. Joint multistrategy scenarios must preserve or explicitly stress common factors, funding/liquidity shocks and crisis tail dependence. Historical scenarios have limited coverage; synthetic scenarios expose assumptions rather than observed frequencies. Do not rank these methods universally or implement advanced numerical financial risk in III.

Portfolio admission compares with/without a candidate under common capital, risk, costs, capacity, information and search budget. Examine exposure factors, signal/position overlap, joint losses/tails, liquidity and marginal risk/return, not correlation alone. A fixed count or capital split does not control risk contribution. Benchmarks and simple allocation remain necessary before a complex optimizer. Record cash contributions/withdrawals separately from returns, and distinguish capital assigned, available, reserved and collateral/margin; allocation changes need versioned rules and actor decisions.

Mature engines remain candidates under the existing [engine admission gate](engines.md). The synthetic harness must not evolve opportunistically into a financial simulator. Before any future adapter, prove order types/precision/minimum size, costs/spread/slippage/latency, partial fills/rejections/cancels, rate limits, idempotent recovery, financing/margin/liquidation/capacity and reconciliation for the actual instrument/venue semantics. Historical backtest, deterministic event replay, no-order shadow, internal paper, exchange testnet and live have different clocks, liquidity, fills and guarantees; common strategy logic does not make their execution equivalent. Paper remains a first-class inactive future module.

## 9. Audit, research controls and counterfactuals

Six separate guarantees must be described:

1. **Record integrity:** bytes/schema/hash/version and append-only mutation rules.
2. **Provenance:** source/provider/version and what information was known when.
3. **Completeness:** whether expected events/records are missing.
4. **Synchronization continuity:** sequence/watermark gaps, reconnect boundaries and stale snapshots.
5. **Accounting correctness:** cash, positions, fees, flows, margin and assignments reconcile under the model.
6. **Independent verification:** a distinct reference or procedure confirms the conclusion.

Current hashes and tests provide bounded local checks, not proof of source truth, complete external history, external reconciliation, or resistance to a malicious administrator. Event hash chains are unnecessary now; they would not solve those gaps. Future external event ingestion needs provider-scoped event IDs, idempotent application, revisions linked to earlier versions, event/receipt times, reconciliation snapshots and explicit gaps. A balance match alone does not reconcile order state, per-instrument holdings, funding or virtual allocations. Preserve late corrections and missing-event resolutions without silently editing the past. Transactional inbox/outbox patterns are future options where cross-process/external side effects require them.

Current tests cover availability ordering, delayed transformation clocks, final-partition denial, immutable input/code identity, duplicate technical orders, interrupted history and temporal plans. Add prefix/truncation or future-input perturbation checks for each new causal transform; when recursive indicators arrive, test convergence across justified warm-up lengths and historical/prospective parity. Such checks do not prove that a universe includes delisted assets, that publication vintages are correct, or that model selection avoids leakage. Those need dataset audits and preregistered IV/V controls. Freqtrade-style lookahead/recursive diagnostics are useful references with detection limits, not a certificate or required dependency.

A future intervention journal pins the policy and information available at decision time, initiator type (human/AI/protection), proposed and actual actions, approved scope, confirmation, unchanged assumptions and later observations. A shadow path can estimate what the prior policy would signal, but requires separate prospective authorization and resources. Its hypothetical fills, impact and liquidity differ from observations. Label modeled counterfactuals with uncertainty; a later market recovery does not prove a prudent intervention was an error.

## 10. Navigation and implementation order

Keep the implemented six sections—overview, hypotheses, datasets/chart, experiments/results, module inventory and audit—while those are the real services. A future organization can group **Research** (hypotheses, models, experiments, proposals and archives), **Operations** (instances, deployments, health and execution), and **Portfolio & Risk** (exposures, capital and decisions), with cross-links into shared audit/evidence. Do not create thirteen empty pages or a duplicate “strategy factory” application. The section registry and chart adapter support additive sections.

Each future chart should carry dataset/record references, sample interval and timezone, units/currency, method/transform version and relevant availability constraints. Compute scientific statistics in the backend; frontend interaction may select/render already authorized results. Equity/drawdown, scenarios, correlations, execution quality and comparisons remain future until genuine data/calculation services exist. The UI must preserve uncertainty, synthetic labels and unavailable/failed states; visual polish is not a scientific acceptance criterion.

Order of work:

1. Finish and verify current III services; preserve local work and the original A–F gates.
2. Add the small immutable reference extension and its historical-version/hash-denial tests. Amend architectural semantics without rewriting existing v1 records.
3. Finish clean install/build/startup and actual browser integration; align status labels and EN/ES documents with evidence.
4. Record the future admission requirements above. Do not add empty operational entities, new dependencies, scheduled investigations or financial computations merely to satisfy a matrix row.
5. Seek the separate authorization required for IV and later work only after presenting verified III scope and outstanding limitations.

The reference addition is compatible: optional empty hypothesis associations preserve existing technical callers; exact references are frozen for new linked attempts; any schema/version change must retain an explicit old-record reader rather than mutate history. Existing generic document storage does not need a new database table for this extension. Operational position/capital ownership and external reconciliation **must be settled before their first persistent adapter**, not deferred until live deployment; they are not dependencies of today's synthetic chart or hypothesis catalog.
