This bounded review addresses decisions that could change the architecture. It examines **six new official technical pages**, plus a verified MLflow snapshot already examined in III.A. It does not reopen Phase I, add financial evidence to its 53 studies, install engines, download market history or execute their examples. The previous [engine](engines.md) and [research-tool](research-tools.md) comparisons remain valid within their recorded scope. Documentation establishes what a project describes; it does not independently validate an implementation or prove economic advantage.

## Minimal conclusions and alternatives

**Use explicit relationships before more services.** The current generic versioned record store and typed contracts can carry stable internal identities, pinned evidence references and separate decision records. That avoids one table for every noun while preserving a path to indexed relational projections if real workload demands them. Provider order IDs or magic numbers belong to scoped external references; they are not universal identities. This is a project design judgment supported by the ownership/version problems above, not a claim that any reviewed engine uses our exact schema.

**Separate a state description from a grant.** Scientific status, implementation maturity, runtime session, operational condition and capital eligibility should remain independently recorded. A review can approve a proposal without confirming an action occurred. A retired strategy's new review must not resurrect a former authorization. Existing role/mode denial remains authoritative in III. No workflow framework was needed to establish these invariants; adding one before an actual cross-process approval workflow would introduce configuration and migration cost without demonstrated benefit.

**Keep risk independent, without pretending every action is interchangeable.** Preventing new exposure, canceling working orders, reducing an attributed position and closing a venue's net position have different consequences. The reviewed execution/reconciliation behavior supports documenting these as separate future intentions/results. Unknown venue state calls for a scoped containment/reconciliation policy; it does not justify assuming flatness or sending an unconditional opposite order. The synthetic harness cannot certify these future policies.

**Prefer structured history retrieval first.** The present hypothesis, dataset, run/failure, proposal and audit records already provide stable fields for exact filtering and evidence links. Future retirement/review records can preserve reasons, uncertainty and reconsideration conditions without becoming a visually separate “graveyard” application. Semantic search/RAG may later help find related text, but retrieval relevance is not evidence validity, generated explanation is not observation, and no vector database, knowledge graph or LLM retraining is justified solely by the number of records. This is an architectural comparison, not a benchmark of retrieval quality; those tools were not installed or tested here.

**Design monitoring as evidence, then policy, then action.** Technical freshness/latency/continuity and statistical change are different channels. Data drift changes inputs; concept drift changes a conditional relationship; model degradation concerns predictive performance; execution degradation concerns realized execution; alpha decay concerns net economic advantage. One may contribute to another, but none establishes the others automatically. The NIST source supports specifying detection/error tradeoffs, not selecting a detector for this project. A future protocol must account for serial dependence, overlapping windows, repeated looks, multiple monitors and reset/review behavior. No monitoring metric grants production authority.

## Proportionate technical checks and deferred evidence

The coverage report maps the supplement's proposed tests to implementation. The source review justifies these small checks now, when their contracts exist:

- An immutable version reference resolves the same bytes after a new version or alias is introduced; separate instance/session identities do not overwrite one another.
- An approval record has no execution effect; a terminal or retired status does not restore a grant.
- A causal transformation produces the same earlier outputs after future rows are appended, propagates delayed availability, and does not emit pre-warm-up results. A deliberately leaky fixture should fail the same check.
- Duplicate synthetic event identities cannot book quantity/cash twice. Correction semantics remain explicit rather than being simulated as an unrelated trade.
- Reserved data remain denied through reports, charts, worker execution and newly added evidence links.

These tests do **not** validate market feeds, survivor universes, financial engine fills, cross-venue netting, real reconciliation, drift calibration, portfolio contribution, Monte Carlo tails or live interventions. Such work requires the corresponding data/protocol/authorization gates. C1–C5 and the no-financial-experiment boundary are unchanged.

## Evidence limits and stopping rule

All six new retrievals returned substantive official HTML; the register records hashes, URLs, dates and directed reading scopes. The MLflow reuse hash matched its previous receipt. Pages labelled `latest`/`stable` are moving documentation targets, not exact package locks. We have not audited underlying implementations, licensing changes beyond the existing III.A review, every linked page, governance correctness, performance or statistical behavior on cryptocurrency data. No private reference platform was inspected and no superiority is inferred from it.

The six-page budget is complete. Stop this expansion: no additional framework search is needed to decide the minimal compatible records/controls and deferred capabilities. Reopen only if an identified implementation or adapter decision cannot be resolved by these records and a bounded specific source check would change it.
