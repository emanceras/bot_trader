## Findings that change a concrete decision

1. **Names do not establish equivalent information.** Official Kraken WS trade-side meaning is the taker side; Coinbase Exchange match-side meaning is the maker side. Binance archive/live timestamp units can differ; a candle update can be incomplete. Source adapters must carry original definitions, versions and identities before producing a shared representation. Current corrected history cannot be made first-received history by assigning an invented receipt time.
2. **The existing PyArrow ceiling is revisable.** Git history places `>=19,<24` in the initial core commit `2cf79b4`; the inspected decision history supplies no specific incompatibility rationale for 24+. The lock uses Arrow 23.0.1 and DuckDB 1.5.6. Nautilus 1.231.0's installed requirement `>=25` conflicts with that current constraint, but does not prove upgrading is unsafe or impossible. DuckDB/Arrow interoperability documentation is not certification of an exact version pair.
3. **Higher precision must survive the whole path.** DuckDB 1.5 documentation warns that timezone-aware nanosecond input converted to `TIMESTAMPTZ` loses sub-microsecond precision. Proposed canonical events retain integer epoch ticks, explicit unit/precision and clock/calendar metadata; conversions must reject silent loss. This is a future contract requirement, not a retroactive change to the microsecond synthetic v1 data.
4. **Nautilus's support line matters as much as dependency resolution.** The inspected upstream develop README describes security-only v1 backports and a different v2 release-candidate API with a production warning. These are branch/documentary statements, not a new installed-version test. Updating Arrow alone does not settle this risk. LEAN merits equal evaluation; its own default fill/impact assumptions and restart/state requirements also need tests.
5. **Missing source evidence remains missing.** A Tardis client-documentation response returned HTTP200 with “Page Not Found.” Databento's inspected catalog establishes a relevant future multiasset option, not verified historical/live parity, prices or entitlements. Reuse prior evidence with its dates; do not count generic pages or source popularity as admission.

## Recommended target boundary, without rebuilding

Maintain one platform with source-specific ingestion and instrument mapping, a versioned canonical event layer, shared causal transformations and decision logic, and replaceable execution/accounting adapters. Preserve raw versions when their scientific and rights value justifies retention. Store derived bars/features by parent versions, aggregation/calendar configuration and transform version; deterministic batch/replay/live paths must share those definitions. Keep as-observed and corrected-history views distinct.

The common contract must represent what is known and unknown rather than force all assets into a spot base/quote or always-positive-price schema. Future equity actions, futures expiry/multiplier/settlement, FX volume conventions, nontradable indices and venue calendars are typed capabilities admitted before their dependent use. They do not create a requirement to build those modules now. Do not introduce another UI, a universal mega-schema, a mandatory event broker, distributed microservices or a custom general financial engine.

Prefer **engine-independent logical contracts now, deployment choice after evidence**. For research, an isolated worker can exchange immutable batches with explicit sequence/cutoff/lineage and avoid a per-event network hop. Same-process execution can reduce serialization/coordination and be simpler if a disposable upgrade passes. Neither process isolation nor shared memory proves safety, correct state or exactly-once effects. Startup cost, serialization/copying, backpressure, synchronization, ownership, journal durability and recovery must be measured under the same workload. Future live execution may need a different process boundary for justified operational reasons; do not force research and live to share execution assumptions.

The New York opening example tests architecture only: venue-specific session identity, local timezone/DST, holidays/early closes, auction versus continuous session, first complete interval and receipt-aware availability. No bar duration, trading rule, cross-market hypothesis or additional experiment is selected. A future study must preregister a mechanism-based finite horizon comparison and independent evaluation before observing its results.

Tests of capture/replay against **actual live recordings** would require a separately approved finite collection scope and rights, even when no orders are sent.

| Recurring operation | Future feed, storage/backup, cloud, monitoring, inference and maintenance categories identified | No collector/feed/server subscription authorized. Self-hosted/free software still has operational costs; never confuse a source fee with a trading commission |
| Scientific and economic | Accepted comparative questions and limited search envelope | E3 budget and E4 capital/materiality/risk remain unbound. No source or engine benchmark supplies a profit expectation, power guarantee or live risk tolerance |

Explicitly defer broad provider acquisition, permanent engine selection, a production Arrow upgrade, live capture, news/LLM/on-chain implementation and multiasset strategies. Do not add Kafka/RAG/knowledge graphs or universal live controls solely to make the architecture look complete. Do not build a general financial engine from the synthetic ledger. Reconsider each only for a defined scientific/technical requirement, a finite comparison and attainable resource/rights evidence. Freqtrade's convenience or LEAN's asset catalog is not an economic advantage; installed Nautilus is not a sunk-cost obligation.

The material decisions are grouped:

- **Methodological principle ready for review:** the explicit [staged-admission clarification](evolution/staged-admission.md). Acceptance would change when dependent bindings are completed, not approve financial execution or dilute E1/E2. Until accepted and instantiated, the original protocol/acceptance remain controlling.
- **Technical authorization next, once manifests are fixed:** M/E/R, selecting only the tests that resolve a decisive uncertainty. No need to approve each parser field; exact new package/version/resource commitments are prepared before installation. Same-environment versus worker and the final engine should be decided from these results, not from architecture preference.
- **Evidence-dependent later commitments:** H and any spending, then E3/E4 and separately scoped financial development. Holdout opening and prospective/live operation remain subsequent distinct permissions. No arbitrary capital, margin or risk number is requested now.
