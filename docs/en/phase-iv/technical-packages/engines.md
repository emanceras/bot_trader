## Acquisition and harness boundary to authorize

Allow only these software artifacts after approval: the fixed Nautilus wheel and managed CPython; fixed .NET SDK; the pinned LEAN source files and their declared build dependencies; small deterministic harness code and invented fixtures. Obtain LEAN through a shallow partial, sparse source checkout with no initial checkout and **no financial `Data/` or test/example data bodies**. Select build/source files and licences only. Disable recursive submodule/LFS acquisition and fail if the server cannot honor the partial route; do not fall back to a full source ZIP, image or clone containing datasets. Log acquired paths and transfer sizes.

Build a small C# harness against the required LEAN libraries, with an explicit offline data provider and invented symbol/calendar configuration. Do not start its default Launcher, DownloaderDataProvider, hosted service, paid CLI, optimization tools or example algorithms. Restore only dependencies required by that fixed source graph, save the complete resolved NuGet lock and package hashes, then use locked restores. Unresolved/dynamic dependencies or a build requiring financial sample bodies stop the route. No container engine, daemon, Redis/database server or new external service is included.

The supervisor sends the same versioned JSONL inputs to the C# LEAN and Python Nautilus harnesses and consumes normalized observations. Use integer epoch nanoseconds with declared supported precision, IDs/sequence, event/receipt/availability, explicit currencies and Decimal strings. Configuration, initial state, command IDs and artifact hashes are shared. No sockets to venues or credentials are configured; deny runtime network access after setup. Logs must expose unsupported precision or event types, never round silently.

This proves only a narrow **engine boundary for external strategy decisions**. It does not certify LEAN's Python.NET embedding, Python strategies inside LEAN, a full financial adapter, native multibot allocation, derivative economics, Windows or live connectors. Those are not needed to distinguish the initial offline engines. Native capabilities, explicitly configured fill models and harness-supplied guards/attribution must be labelled separately. The oracle computes expectations; it may not inject those expected fills and call that a native engine pass.

Only configure existing engine fill models in this package; do not implement a new liquidity/fill model. If such a model is necessary, label the dependent case unsupported and document the future integration requirement. A handwritten expected-fill emitter cannot count as a native or configured-engine pass.

## Fixed common functional cases

Before inspecting outputs, hash one bundle with an invented spot instrument, two virtual strategy IDs, one shared account, explicit USD and USDT cash ledgers, an invented conversion quote with known availability, and no leverage. Fixture prices, quantities, fee rates, times and balances are arithmetic test values, not proposed market costs, capital or scientific horizons. Freeze currency/tick/quantity precision and rounding rules. Integer money/quantity units must reconcile exactly; no result-fitted tolerances.

| Case | Shared stimulus | Mandatory acceptance for the tested offline boundary |
|---|---|---|
| E1 — causal input and decisions | Consume the R bundle's delayed closed-bar, revised-event and equal-event-time/different-availability canaries; send a trivial predetermined technical decision rule through the supervisor | Identical admitted information, initial state and rule give identical decision/command digests. Future or unavailable values cannot affect an earlier command. Explicitly reject unsupported time precision; calendars are supplied fixture metadata, not an equity strategy |
| E2 — cash, fees and rejection | Scripted buy/sell, maker/taker cases, partial quantity, invalid step/minimum, insufficient free cash and USD/USDT conversion missing/present | Actual fills/fees/reservations reconcile to independent Decimal equations; fees occur once; free/reserved/total cash and inventory are distinct. Reject invalid commands and unsupported conversions rather than assume USDT=USD |
| E3 — finite liquidity, two variants | First expose one unit at L1 and submit a larger market order; then provide a fully specified finite L2 book with GTC/IOC, partial fill, cancel-before-fill and fill-before-cancel | No undocumented invented depth; conserve filled/open/cancelled quantity and depth consumption. Native L1 overfill remains an adverse result. If native finite-depth semantics are absent, report unsupported or a separately labelled model requirement. Do not replace market with IOC to erase failure; FOK/queue inference is deferred |
| E4 — duplicate and shared-capital canary | Repeated command/fill IDs, equal-valued distinct fills and two labelled intents competing for the same cash | No double fee/fill/reservation; same-value new ID is not discarded. Broker net position equals summed virtual attribution, without duplicating capital. A simple deterministic first-accepted reservation policy is a harness test rule, not approval of portfolio netting/allocation |
| E5 — actual interruption, three cut points | One uninterrupted reference; then kill the worker (a) after submission before acknowledgement, (b) after fixture venue fill before local checkpoint, (c) during cancellation. Persist the same fixture venue journal and resume the same run ID | Reconcile pending/terminal orders, fills, balances and positions with the persisted independent fixture source before new commands. No replayed command may cause another financial effect. Preserve unknown state and block new actions if reconciliation is incomplete. A fresh unrelated replay does not pass |

Functional budget per engine: **nine runs** — E1, E2, two E3 variants, E4, and E5's reference plus three interrupted continuations. Each functional journal has at most **256 source events and 32 commands**; these bounds keep the hand-checkable oracle finite. A crash/restart belongs to the same test attempt, not an independent result. A decisive native failure can stop dependent cases, while independent checks/other engine continue within the fixed envelope.

E5 may use native restoration or deterministic reconstruction from the **same durable journal** with idempotent suppression of already applied effects. State which mechanism works, what is persisted, its replay cost and which component supplies it. A harness journal does not prove native exchange reconciliation or a production-ready recovery system. If recovery needs a general adapter/service beyond this bounded bridge, stop and report that missing implementation rather than build it under E.

## Resource measurement and stopping rules

After functional admission, E6 measures one fixed workload per engine: **10,000 invented events, 100 scripted commands, two instrument IDs and two strategy labels sharing one account**, with the same event shapes, arrival order and explicit liquidity model. Run once cold and three times warm, sequentially; retain all observations. This is **four resource runs per engine**, hence at most **26 initial functional/resource runs** across both candidates. No load sweep, strategy fitting or optimization. If functional gates fail, do not produce an attractive throughput score for that failed route.

Separate setup/build, startup, supervisor serialization, processing, reconciliation and storage costs. Report wall/CPU time, peak process-tree RAM, scratch bytes and full latency summaries; a tiny sample cannot establish production tail latency. Faster execution cannot compensate for wrong accounting. There is no invented mechanism-independent throughput requirement; admission here means finite correct completion within the resource ceiling, not suitability for subsecond trading.

| Resource | Planning estimate, not a measurement | Hard proposed scope ceiling |
|---|---|---|
| Host | Existing Linux x86_64; run engines sequentially, retaining separate locks | At most 4 CPU cores and 8 GiB process-tree RAM; no paid/cloud expansion |
| Software transfer | Approximately 0.4–1.5 GiB including SDK/runtime/build packages; Nautilus wheel size alone is exact | **2 GiB total** for E installation/source/dependencies; check advertised sizes when available and enforce cumulative actual bytes. Unknown totals are not a licence for unbounded restore |
| Scratch and artifacts | Approximately 1–5 GiB including expanded binaries, source/build caches and logs | **8 GiB** total E workspace; preserve small receipts/failures before cleanup, no raw binaries in Git |
| Machine time | Approximately 1–2 hours for first setup/build and finite tests; caching and host contention may change this | **4 hours cumulative** setup/build/execution; **10 minutes per functional attempt**, **20 minutes per resource attempt**, each bounded by the total |
| Engineering effort | Approximately **2–4 working days** to write/review both minimal harnesses and interpret differences; not a completion promise or CPU time | Stop for a scope-expanding adapter requirement. Any new implementation beyond the declared bridge needs a new decision, not silent extension |

Stop acquisition before a cap is exceeded; if a tool cannot enforce the transfer/resource envelope, block that installation route. Record exact pinned packages, resolved dependency hashes and failures before tests. No automatic SDK/engine patch upgrades, native source-build fallback for Nautilus, third engine, broadened workload or changed oracle. One corrective harness revision may rerun only directly affected cases for a diagnosed harness defect; preserve original outputs and consume the same time/storage caps. An engine limitation or disputed hypothesis is not a harness defect. Record every invocation, including aborted cases and reruns: at most 26 initial case attempts plus 26 directly affected one-time repair reruns, 52 total. Worker restarts within a cut-point case are logged as process invocations, not extra independent cases. The same resource ceilings cover all attempts.
